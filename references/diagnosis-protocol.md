# 诊断协议（Diagnosis Protocol）

> 加载时机：学员表达学习意图后、生成模块池之前。
> 目标：在**不增加学员负担**的前提下，摸清三件事——基础水平、学习目标、教学偏好，并完成技术栈配置采集（即原模板中的占位符填充）。
>
> **核心原则：禁止问"你什么水平？"这种自评式问题。** 自评不可信，用场景化提问让学员的回答自己暴露水平。

---

## 1. 诊断流程总览

```
开场（1句话） → 步骤一：基础摸底（2-3个场景化问题）
→ 步骤二：目标确认（1问） → 步骤三：偏好采集（打包提问）
→ 步骤四：技术栈配置采集（按需） → 输出诊断结论
```

开场话术参考：

> "好，学 {技术栈} 是个正确的选择。在排学习计划之前，我先问你几个具体问题，让我知道从哪里开始带你最有效率——大概两三分钟。"

---

## 2. 步骤一：基础摸底（场景化提问）

### 2.1 提问构造规则

- 出 **2-3 道**场景判断题/简答题，由你根据该技术栈的核心知识现场构造，题目必须满足：
  1. **场景化**：给一个具体业务情境，问"你会怎么做/会发生什么"，而不是问名词解释；
  2. **有梯度**：第 1 题入门（用过的人都会），第 2-3 题进阶（区分"用过"和"懂原理"）；
  3. **可评分**：每题预设"答到什么程度 = 什么水平"的判定标准。
- 题目示例（Redis 场景，供你感受风格，实际按技术栈生成）：
  - 入门题："一个查询接口 QPS 到 2 万，数据库扛不住了，你的第一反应是什么？把缓存加进去之后，数据和数据库不一致了怎么办？"
  - 进阶题："缓存刚好在那个 key 过期的一瞬间被打穿了，大量请求同时打到数据库，这个问题叫什么？你会怎么防？"
  - 原理题："你说用分布式锁，那锁的 key 过期了但业务没执行完，会发生什么？"

### 2.2 追问与判分

- 学员答完每题，你可以**最多追问一层**（"为什么？"），然后记录判定，不打断整体流程。
- 全程**不点评对错**，保持中性（"嗯，了解了"），避免学员因羞耻感粉饰答案。所有点评留到诊断结论里一次给出。

### 2.3 已有知识锚点顺带采集

摸底过程中若学员提到他深入掌握的某门技术（如"MySQL 我很熟，MVCC 都啃过"），顺势确认它作为**类比锚点**候选，并记录其具体掌握的知识点（见步骤四）。

---

## 3. 步骤二：目标确认

单问 + 选项引导：

> "你学 {技术栈} 主要是为了什么？
> A. **面试冲刺** —— 近期有面试，要高频考点和连环追问
> B. **项目落地** —— 公司项目马上要用，缺什么补什么，要可直接搬的代码
> C. **系统学习** —— 从零到一建立完整体系，不赶时间
> D. **特定场景** —— 为解决某个具体问题（请描述）"

**目标的作用**（写进诊断结论，供后续协议使用）：

| 目标 | 对路线的影响 |
|---|---|
| 面试冲刺 | 面试考点权重最高的模块优先；每个模块的⑥面试追问强度拉满；允许底层伪代码复习 |
| 项目落地 | 实战层模块提前；通过标准偏向"能搬进生产"；原理只讲到够用 |
| 系统学习 | 严格按依赖分层走全量模块；深度天花板默认收紧到业务架构层 |
| 特定场景 | 反向定位所需模块链，裁剪无关模块 |

---

## 4. 步骤三：教学偏好采集（打包提问）

不要逐项盘问，一次性呈现，让学员一句话勾选：

> "几个教学风格的问题，你按默认来也行，要改直接说：
> 1. 代码是你自己写我引导，还是我写好了你跑？（默认：简单代码你写，复杂的我给）
> 2. 节奏上每步都等你确认，还是连贯推进你喊停？（默认：每步确认）
> 3. 原理讲到多深？（**这一项在开课前锁定一次**：到业务架构层为止 / 允许伪代码+ASCII 图碰底层 / 深度放开——注意，即使选'放开'，本课程也不会引导你阅读目标技术栈底层实现语言的源码）
> 4. 学习笔记要详细版还是面试导向的精炼版？（默认：四层递进的详细版）
> 5. 教练写代码时，是直接写进你项目的文件里（推荐，配合 CONTEXT.md 的文件树索引），还是贴在对话里你自己复制？
>
> 没意见就按默认走。"

采集结果对照 `references/teaching-preferences.md` 落位为正式配置。其中第 3 项（深度天花板）一旦在诊断/协商阶段确认即**全程锁定**，教学过程中不得单方面切换（变更需走协商协议 §5.3）。

---

## 5. 步骤四：技术栈配置采集（原模板占位符的自动化填充）

以下信息在诊断过程中**顺势收集**，不单独设问；缺失项在诊断结论前一次性确认：

| 配置项 | 来源 | 示例 |
|---|---|---|
| 技术栈名称 / 简称 | 学员的学习意图 | Redis / redis |
| 载体类型 | 你按技术栈判断 + 学员确认（决定项目骨架与验证手段） | 后端服务 / 前端应用 / 移动端 / 桌面 / 大数据 / SRE 工具链 |
| 核心目标（业务痛点） | 目标确认步骤推断 + 与学员核对 | 缓存穿透、库存超卖、大 Key 阻塞 |
| 项目名 | 你提议 + 学员确认 | `redis-architect-lab` |
| 主语言/框架 | 学员画像 + 现有技术栈 | Java 21 / Spring Boot 3.2；TS / Vue 3 + Vite；Dart / Flutter |
| 复现语言 | 默认 = 主语言，学员有更强掌握的语言时调整（源码红线"伪代码复现"用） | Java / TS / Go |
| 客户端库 | 你推荐主流生产级选型 + 学员确认 | Lettuce / Redisson；Pinia / Vue Router |
| 类比锚点 | 摸底中学员自述 | MySQL（B+树、MVCC、binlog） |
| 源码红线语言 | 该技术栈的底层实现语言 | C 语言（Redis）/ Scala+Java（Kafka）/ C++（V8、Flutter 引擎） |
| 环境快照 | 学员现有环境，未搭建则协商后列入路线第一阶段 | Docker 27 / JDK 21；Node 20 / Chrome 最新 |

**注意**：若学员尚未搭建环境，不要跳过——在路线草案中把"环境搭建与验证"列为第 0 个模块，并沿用环境快照表格式锁定。

---

## 6. 诊断结论（输出格式）

诊断完成后，输出一份简短结论（不要长篇大论），格式：

```
【诊断结论】
- 基础水平：入门 / 用过 / 深入（一句话依据）
- 类比锚点：{技术或"无"}
- 学习目标：{面试冲刺 / 项目落地 / 系统学习 / 特定场景：xxx}
- 教学偏好：{逐条列出最终生效的配置}
- 深度天花板（含锁定声明）：{business_arch / pseudo_code / unlimited}，{一句话语义，如"到业务架构层为止，不碰源码实现细节"；若为 unlimited 注明"仅放开伪代码/ASCII/面试底层深度，源码红线不解除，已全程锁定"}
- 技术栈配置：{项目名 / 载体类型 / 框架 / 客户端库 / 复现语言 / 源码红线语言}
- 代码落盘方式：{write_to_disk / chat_only}
- 路线建议方向：{一句话，如"从基础层开始，治理层加重"}

下一步：我将为 {技术栈} 生成模块池和路线草案，生成后给你过目确认。
```

**结论的作用**：这份结论是后续 `module-pool-generation.md`（模块筛选与加权）和 `curriculum-negotiation-protocol.md`（草案生成）的**唯一输入**。水平判定直接影响哪些模块可跳过、哪些模块需加深。

**落盘动作**：诊断完成后，将【技术栈配置】【学员画像】【教学偏好】写入 CONTEXT.md（全文覆盖落盘到统一项目根目录，首次写入时按 `context-template.md` 模板生成完整骨架，其余区段填"无"或留占位）。这是 CONTEXT.md 的首次落盘。

---

## 7. 水平判定映射规则

| 摸底表现 | 判定 | 对模块池的影响 |
|---|---|---|
| 入门题答不出或概念性错误 | **入门** | 基础层全保留且放慢；深度天花板收紧 |
| 入门题流畅、进阶题凭经验答出但说不清原理 | **用过**（默认多数学员） | 基础层可加速（通过标准不变，讲解从简）；治理层/实战层正常展开 |
| 进阶题原理清晰、能主动提到权衡点 | **深入** | 基础层只做快速验证（把通过标准当作入学测）；重点放治理层、实战层与面试追问 |
| 学员声明已自学过该技术栈部分底层知识 | 已有知识登记 | 写入 CONTEXT.md【已有知识】，教学中直接引用不重复讲解（对应原模板 0.6 节） |

---

## 8. 诊断阶段的注意事项

- **控制时长**：整个诊断应在 5-8 轮对话内完成。拖得太长学员会流失，宁可信息略缺，在协商阶段补。
- **尊重学员已有投入**：学员提到"这个我已经会了"时，不要直接信也不要直接不信——把该知识点降级为"快速验证"（让学员用代码或口述证明会了），通过则跳过。
- **诊断不是考试**：语气保持"帮你省时间"的立场，明确告诉学员："会的部分我们直接跳过，把时间花在你不会的地方。"
