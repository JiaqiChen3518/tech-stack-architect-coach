# 模块池生成协议（Module Pool Generation Protocol）

> 加载时机：诊断完成（通过门禁 A）之后、方案协商之前。
> 目标：为**任意软件开发技术栈**（后端、前端、移动端、桌面、大数据、SRE 工具链）动态生成一个结构化的知识模块池，作为路线协商的素材。
>
> **本协议是通用化的核心**：Skill 目录中不预置任何具体技术栈的教学内容，模块池质量完全取决于你是否严格遵守本协议的粒度标准、分层规则和范例风格。

---

## 1. 什么是"模块"

模块是路线编排与进度追踪的最小单位，必须同时满足：

1. **单一知识点单元**：一个模块只解决一类问题（如"缓存穿透治理"是一个模块，"缓存"不是）。
2. **可验收**：有明确的、可操作的通过标准（见 §5）。
3. **时长有界**：预估 0.5 ~ 2 天可完成。超过 2 天必须拆分成前后两个模块（如"主从复制"与"哨兵"分开）。例外：快速验证模块（学员已声明掌握的知识点，通过标准=入学测）时长可标 0.25 天，见 §8。
4. **可独立讲解**：模块内部遵循六步走（场景→概念→原理→编码→验证→面试），自成闭环。

**反例（禁止）**："Redis 高级篇"（不可验收）、"数据结构与持久化"（两个知识点混装）、"消息队列原理"（超过 2 天上限）。

---

## 2. 分层规则

任何开发技术栈的模块池按以下四层组织。**分层名是逻辑角色，不是固定栏目**——按技术栈实际形态对号入座；非后端载体允许把层的中文名换成同义词（如前端 L3 叫"性能与工程化层"、移动端 L2 叫"运行机制层"），但**层的判定标准不变**，且 **layer 字段必须保留 L1-L4 前缀**（如 `L3 性能与工程化层`），确保协议层引用统一。

| 层 | 判定标准 | 典型内容（后端视角） | 典型内容（前端视角） |
|---|---|---|---|
| **L1 基础层** | 使用该技术的最小必要知识；是后续一切模块的前置 | 核心数据结构/核心模型、连接与序列化、线程/并发模型 | 组件模型、响应式数据流、模板/JSX、路由与状态管理入门 |
| **L2 核心机制层** | 该技术赖以工作的内部机制，生产环境必配 | 持久化/存储机制、索引、事务、副本与一致性协议 | 渲染机制（虚拟 DOM/编译时优化）、更新调度、响应式依赖追踪 |
| **L3 高可用与治理层** | 生产环境的坑与稳定性保障，面试最高频 | 高可用方案、集群、限流降级、容量规划、监控告警 | 性能优化（包体积/首屏/渲染卡顿）、内存泄漏治理、错误监控、工程化 |
| **L4 实战层** | 用该技术解决真实业务问题的组合打法 | 分布式锁/幂等/延迟任务、典型架构落地、压测与调优 | 复杂组件抽象、权限/多语言等中台方案、大型应用架构、发布与回滚 |

**分层映射示例**：

- Redis：L1=数据结构/序列化/线程模型；L2=RDB/AOF/主从；L3=哨兵/Cluster/缓存三坑/大Key/内存淘汰；L4=分布式锁/Lua/监控
- Kafka：L1=Topic/Partition/生产者消费者；L2=存储机制/副本与 ISR/位移管理；L3=重平衡/ exactly-once/积压治理；L4=延迟队列/事务消息/压测调优
- MySQL：L1=索引与执行计划；L2=事务与 MVCC/日志体系；L3=锁/主从复制/分库分表；L4=慢查询治理/线上故障复盘
- Vue：L1=组件与响应式基础/Pinia；L2=渲染与更新机制/编译优化/响应式依赖追踪；L3=性能优化（首屏/包体积/长列表）/内存泄漏/错误监控；L4=复杂状态方案/组件库封装/大型应用架构

## 3. 模块元数据规范

每个模块必须携带以下元数据（协商协议和教学阶段都依赖它）：

```yaml
---
id: <两位序号，拓扑序>
title: <模块名，动宾或名词短语，如"缓存穿透治理">
layer: <L1 基础层 / L2 核心机制层 / L3 高可用与治理层 / L4 实战层>
difficulty: <入门 / 进阶 / 实战>
prerequisites: [<依赖模块 id 列表>]
goals: [<适用目标：面试冲刺 / 项目落地 / 系统学习>]
duration: <0.5 / 1 / 2 天>
priority_by_goal:
  面试冲刺: <1-10>
  项目落地: <1-10>
  系统学习: <1-10>
---
```

**priority_by_goal 的填写规则**：
- 该技术栈面试中最最高频的考点模块打 9-10（一般全池只有 2-3 个）；
- 高频打 7-8；中等 5-6；冷门但成体系必需的 3-4；边角知识 1-2。
- 按目标生成推荐路线时，以对应目标列的优先级降序为主排序键、依赖拓扑为约束。

## 4. 生成流程（五步法）

```
第1步 建立知识地图：列出该技术栈的核心知识体系（10-16个候选知识点）
第2步 知识点归层：按 §2 的四层判定标准，把候选点归入 L1-L4
第3步 拆分与合并：按 §1 的粒度标准校准——超 2 天的拆，不足 0.5 天的合并
第4步 标注元数据：为每个模块填 §3 的元数据（依赖、优先级、时长）
第5步 质量自检：逐条过 §6 检查清单，不通过则回到对应步修改
```

**知识地图怎么列**（第 1 步的实操）：
- 依据你的训练知识，列出该技术栈"一个高级开发者（按载体类型：后端/前端/移动端……）必须掌握"的知识点清单；
- 对照官方文档的章节结构和主流面试考点清单交叉验证，确保没有结构性遗漏；
- 规模参考：最终模块数 **8-14 个**。少于 8 个通常是粒度太粗；多于 14 个通常是切得太碎（学员看不完，协商成本高）。

## 5. 通过标准的写法规范（硬要求）

每个模块必须有"通过标准"，写法必须满足：

1. **可执行**：是"做一件事 + 看到什么结果"，不是"理解某概念"。
   - ❌ "理解 RDB 和 AOF 的区别"
   - ✅ "在项目中同时开启 RDB 和 AOF，制造一次宕机，用日志证明数据恢复到了哪个时间点；并能口述两种持久化各自的取舍"
2. **量化或可视化**：验证给出数值门槛——后端压测（"P99 < 10ms""QPS 从 800 提升到 5000"）、前端性能（"Lighthouse 性能分 ≥ 90""首屏 LCP < 2.5s""包体积减少 40%"）、移动端（"冷启动 < 1s""内存峰值 < X MB"）；原理给出可观察证据（如"在日志/火焰图中看到 XX"）。
3. **与六步走对齐**：通过标准落在第 ⑤ 步（验证）——即"验证"环节的通过条件；第 ⑥ 步（面试追问）另行附 2-3 道该模块的连环追问。

### 5.1 载体类型 × 验证手段 × 量化指标

通过标准的量化指标必须按学员技术栈的**载体类型**从下表对应行中选取，不得只写"性能变好""更流畅"这类空话：

| 载体类型 | 主要验证手段 | 量化指标示例 |
|---|---|---|
| 后端服务 | 压测 / 集成测试 / 日志分析 | P99 延迟、QPS、错误率、DB 查询次数、恢复时间 |
| 前端应用 | Lighthouse / 构建产物分析 / 单元测试 | LCP、性能分、包体积、内存峰值、覆盖率 |
| 移动端 | 真机调试 / Profiler / 自动化测试 | 冷启动时间、帧率、内存峰值、包体积、崩溃率 |
| 桌面 | Profiler / 安装包分析 | 启动时间、内存占用、二进制体积 |
| 大数据 | 任务跑批 / 数据校验 | 吞吐、延迟、数据一致性抽查通过率 |
| SRE 工具链 | 故障注入 / SLI/SLO 观测 | 可用性、MTTR、告警覆盖率 |

> 载体类型在诊断阶段采集（见 `diagnosis-protocol.md` §5）。若一个模块横跨多种验证手段，取该模块主战场对应的指标。

## 6. 质量自检清单

模块池生成后，逐条自检，全部通过才允许进入协商阶段：

- [ ] 模块数在 8-14 之间
- [ ] 每个模块都有明确的 layer、prerequisites、duration、priority_by_goal
- [ ] 依赖图无环；L1 模块无前置；每个模块的前置都在它之前
- [ ] 每个模块都有可执行的、量化的通过标准
- [ ] 覆盖了该技术栈"面试最高频"的至少 80% 考点
- [ ] 有一个贯穿全课程的统一项目载体，每个模块的"实战落地"都能在其中落类
- [ ] 难度曲线平滑：不存在"前一模块入门、后一模块突然实战"的无铺垫跳跃（除非诊断显示学员深入）

**单模块示例（05 缓存三大坑，展示完整元数据 + 通过标准 + 面试追问的形态）**：

```yaml
---
id: 05
title: 缓存三大坑治理（穿透 / 击穿 / 雪崩）
layer: L3 高可用与治理层
difficulty: 进阶
prerequisites: [01]
goals: [面试冲刺, 项目落地, 系统学习]
duration: 0.5
priority_by_goal: {面试冲刺: 10, 项目落地: 9, 系统学习: 7}
---
```

- **场景引入**：数据库里不存在的 id 被恶意请求刷爆；热点 key 过期的瞬间被打穿；一批 key 同时过期导致 DB 雪崩。
- **概念解释**：穿透（查不存在的数据）、击穿（热点 key 过期瞬间）、雪崩（大面积同时过期或 Redis 宕机）——三者成因不同，治理手段不同，面试官最爱让你逐个对比。
- **原理简述**：到业务架构层为止——null 值缓存/布隆过滤器挡穿透；逻辑过期+互斥锁挡击穿；过期时间加随机抖动+多级缓存+熔断限流挡雪崩。
- **实战落地**：在统一项目的 `cache` 包下实现三个 `*Protector` 组件，分别对三种场景做防护，压测脚本模拟攻击流量。
- **通过标准**：用 JMeter 模拟 1 万个不存在 id 的请求，DB 查询次数 < 50 次；热点 key 过期瞬间数据库峰值 QPS 不超过基线的 1.2 倍；口述三坑成因与治理的对应关系，不混淆。
- **面试连环追问**：① 布隆过滤器判不存在一定准确吗？② 互斥锁重建缓存时，锁内线程挂了怎么办？③ 雪崩时先限流还是先熔断？为什么？

## 8. 与诊断结论的联动规则

生成模块池时，必须按 `diagnosis-protocol.md` 的诊断结论做以下调整：

1. **学员水平 = 深入**：
   - 该学员声明已掌握的知识点所在模块，降级为"快速验证模块"（时长标 0.25 天，通过标准 = 入学测）；
   - L1 层整体优先级下调，把省下的时长让给 L3/L4。
2. **学员水平 = 入门**：L1 模块 duration 不变但 priority_by_goal 上调；确认路线时提示总时长可能拉长 20-30%。
3. **目标 = 面试冲刺**：按 `priority_by_goal.面试冲刺` 降序提出推荐顺序（仍受依赖约束）；L4 中面试优先级 ≥8 的模块不可裁剪。
4. **目标 = 项目落地**：L4 实战层提前到 L3 治理层之前；通过标准全部改写为"产出可复用代码 + 验证达标（压测/Lighthouse/测试通过率等，随载体类型）"。
5. **目标 = 特定场景**：以场景反推所需模块链（如"我要做订单超时关闭"→ Kafka 池中的 01→03→08→12），链条外的模块标记为"可选"，交由学员在协商阶段决定。

## 9. 模块池的输出形态

生成完成后，以**表格 + 单模块详卡**的形式呈现（表格见 §7 示例；单模块详卡按 7.1 的"场景引入→概念解释→原理简述→实战落地→通过标准→面试连环追问"六段展开）。

- 表格 = 协商阶段用的"路线图底稿"；
- 单模块详卡 = 学员确认路线后、教学到该模块时你的教学脚本底稿（教学时再按六步走展开，注意此时尚未进入教学，详卡只写到"通过标准 + 面试题"为止，正文讲解留到教学阶段产出）。
